# ResolveIQ Project Audit

## Executive assessment

ResolveIQ is a credible, functioning portfolio MVP: it combines a React client, FastAPI APIs, SQLite persistence, ticket workflows, audit events, a locally loaded classifier, TF-IDF knowledge retrieval, human review, and database-backed analytics. The audit verified that the classifier and retrieval are real implementations, not hardcoded API responses.

It is suitable for public portfolio presentation, accurate resume inclusion, and technical interviews when described as a local/demo MVP. It is **not ready for enterprise or production use**. Authentication and authorization are absent by design, database and deployment operations are not production hardened, and the synthetic classifier evaluation does not establish real-world performance.

| Public GitHub portfolio | Ready with caveats | The configured remote responded and the audited baseline was clean. The tracked-file scan found no common secret patterns; Gitleaks was not installed, so this is not a comprehensive secret scan. ## Scope and evidence

The audit reviewed the ticket models and services, API routes and schemas, classifier/training pipeline, knowledge loader and retrieval service, React pages and API client, backend tests, frontend scripts/configuration, seed data, and the README and existing reports. No application source behavior was changed for this audit.

At the start of the audit, the repository was clean at commit `008f750` on `main`; `origin` resolved to the same commit. The classifier artifact existed locally and was ignored by Git. It is generated by the documented training script rather than committed.

## Implemented functionality confirmed in source

- **Ticket management:** SQLAlchemy ticket, suggestion, and event models; Pydantic validation; create/list/read/update/status/history routes; pagination, filters, and search; server-assigned IDs and timestamps; validated transitions; and event recording for workflow changes.
- **Atomic workflow operations:** Service functions group ticket/suggestion mutations with their audit events in database transactions. Suggestion decisions are persisted and audited; accepting a suggestion does not resolve a ticket. Escalation changes assignment/status and creates history.
- **Analytics:** Summary values are queried from SQLite. The documented acceptance denominator is reviewed suggestions (`accepted + edited + rejected`); pending suggestions are excluded. Average resolution time excludes invalid negative durations and is null when no valid resolved-ticket sample exists.
- **Classification:** A cached local scikit-learn `Pipeline` (`TfidfVectorizer` plus `LogisticRegression`) is loaded from a joblib artifact. The API calls `predict` and `predict_proba`; it does not train on requests. Category-to-team routing is a deterministic map. Priority is a separate, explainable substring-rule recommendation, not an ML prediction.
- **Knowledge and suggestions:** Markdown articles are parsed, chunked deterministically, and indexed with TF-IDF/cosine similarity. Search returns ranked chunks and source references. Suggestions extract steps from retrieved content, warn that scores are raw similarities, require human review, and return no instructions when evidence is insufficient. No LLM is called by the default implementation, and retrieved text is not executed.
- **Frontend:** The React/Vite application has live API integration for ticketing, analysis, knowledge, review/escalation, and analytics. The current package scripts provide lint and production-build checks, but no automated frontend test or browser E2E command.
- **Fictional data:** The tracked seed and model-training data are described as fictional; requester examples use reserved `example.com` addresses. The README and AI documentation clearly label evaluation as synthetic.

## AI implementation and evaluation

The code path is genuine: `load_classifier()` loads and validates the locally persisted scikit-learn pipeline, and `analyze_ticket()` invokes its fitted classifier and probability output. The artifact is cached for the process lifetime. Team routing and priority rules are deterministic application logic, not trained models.

The committed evaluation is explicitly synthetic:

- 108 generated fictional records across six labels.
- Seed `20261113`.
- First fold of `StratifiedGroupKFold` with 81 training and 27 held-out rows; scenario variants are grouped together.
- The recorded cross-split maximum normalized similarity is `0.7344`, below the `0.88` rejection threshold; no exact duplicate was reported.
- Recorded held-out accuracy and macro F1 are both `1.0000`, with only 3–6 test examples per class.

These are measured results for a small templated dataset only. They are not real-world accuracy claims. The low-confidence smoke outputs above illustrate why the review flag and advisory-only behavior matter. Confidence is not calibrated, and performance on representative real support requests has not been evaluated. The knowledge service is extractive; there is no configured or used LLM provider.

## Findings and prioritized improvements

### A-01 — SQLite timestamp timezone is lost on reload

**Priority: P2 (correctness).** Ticket columns declare `DateTime(timezone=True)` and are created with UTC-aware datetimes, but SQLite returns naive datetimes when rows are loaded. The isolated round-trip probe reproduced an aware UTC value at creation and a value with `tzinfo=None` after reload; the response then serialized without `+00:00`. Consumers may interpret that timestamp in local time, and the API is inconsistent between freshly created and subsequently read records.

**Recommendation:** normalize timestamps at the SQLAlchemy type or API-schema boundary, define naive SQLite values as UTC explicitly, and add create/read/history/suggestion regression tests. Do not rely on browser-local interpretation.

### A-02 — Documentation says classification is opt-in, but ticket details run it automatically

**Priority: P2 (behavior and transparency).** [PROGRESS.md](./PROGRESS.md) says analysis is opt-in. In contrast, [TicketDetailsPage.tsx](../frontend/src/pages/TicketDetailsPage.tsx) calls the analysis API from an effect whenever ticket details load; the page also has a retry action. The analysis is local and does not update saved category/priority, but opening a detail page automatically sends the title and description to the backend for inference.

The optional `business_impact` value is used in the new-ticket preview but is not part of the persisted ticket model. The later detail-page analysis omits it, so its priority recommendation may differ from the preview.

**Recommendation:** make detail-page analysis explicitly user-triggered or clearly disclose automatic analysis, and decide whether business impact should be persisted and included in later analysis.

### A-03 — No authentication or server-verified identity

**Priority: P1 before any real users or enterprise data.** Demo actor/reviewer labels are attribution fields, not authenticated identities. A caller can use the API without proving the identity represented by a demo reviewer. CORS is not authentication or authorization.

**Recommendation:** add an identity provider or authentication layer, server-side RBAC for ticket/review/escalation actions, and derive audit actors from verified principals before handling non-fictional data.

### A-04 — Database lifecycle and deployment controls are MVP-only

**Priority: P1 before production; P2 for portfolio reproducibility.** SQLite and `Base.metadata.create_all()` support local startup but do not provide managed schema migrations, production backup/restore, retention, or multi-instance coordination. The repository has no production deployment controls, rate limiting, or operational monitoring/alerting. Backend dependencies in `backend/requirements.txt` are unpinned; a fresh install can resolve different versions over time.

**Recommendation:** add a migration workflow, define backup/restore and retention, constrain dependencies, and design deployment-specific secrets management, TLS, rate limits, monitoring, and database concurrency before any production rollout.

### A-05 — Frontend behavior is not covered by automated tests

**Priority: P2.** `frontend/package.json` defines lint, build, dev, and preview scripts, but no test script. Lint and type/build checks do not prove that forms, navigation, error states, or mutation refreshes work in a browser. Earlier manual checks are documented, but they are not a repeatable regression suite.

**Recommendation:** add a small automated browser suite for ticket creation, filtering, suggestion review, escalation, and dashboard refresh against an isolated backend database.

### A-06 — Test-client dependency warning and limited backend reproducibility

**Priority: P2.** The current backend suite passes, but emits a Starlette deprecation warning about `httpx` use with `starlette.testclient`. Backend requirements also have no version constraints or lock file.

**Recommendation:** choose and pin a compatible FastAPI/Starlette/test-client dependency set, resolve the warning, and verify installation from a clean environment.

### A-07 — No explicit repository license

**Priority: P2 for public reuse.** The README correctly states there is no `LICENSE` file. A public GitHub repository is viewable, but users should not infer permission to reuse or redistribute its code.

**Recommendation:** choose and add an appropriate license if reuse is intended; otherwise retain the explicit no-license notice.

## Known limitations

- No authentication, authorization, RBAC, or trusted audit identity.
- Local SQLite only; no migration framework or production operational controls.
- Synthetic data and evaluation only; no representative real-world model validation or probability calibration.
- Priority rules use substring cues; they can miss context or match a cue without understanding impact.
- Retrieval similarity scores are not probabilities; extractive guidance can still be inappropriate and requires human verification.
- No automatic ticket resolution, command execution, or default LLM generation.
- No automated browser E2E suite; no fresh browser interaction run was part of this audit.
- No dedicated secret scanner or dependency vulnerability scan was run for this audit.
- No explicit open-source license.

## Recommended next steps

1. Fix and test UTC timestamp normalization (A-01).
2. Resolve the opt-in/detail-page behavior and decide how business impact should be handled (A-02).
3. Keep the system demo-only until authentication, server-verified roles, and operational security controls exist (A-03, A-04).
4. Pin backend dependencies and resolve the TestClient deprecation warning (A-06).
5. Add automated browser regression coverage (A-05).
6. Evaluate classification and retrieval with appropriately authorized, representative data before making operational claims; calibrate confidence if it will drive review policy.
7. Add a license if public reuse is desired (A-07).

## Bottom line

ResolveIQ demonstrates a real, integrated software workflow suitable for a portfolio and technical discussion. Its strongest interview value is the combination of persistent state, explicit human review, source attribution, and honest synthetic-data caveats. Present it as a functional educational MVP, not as a validated enterprise support product or a model with proven real-world accuracy.
